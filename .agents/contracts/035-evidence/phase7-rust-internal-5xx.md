# Phase 7 — Genuine Rust internal 5xx (OIDC/JWKS dependency failure)

Round-3 reopening item E2. A prior round-3 attempt (`remediation-error-path-rust.md`) claimed a
genuine Rust internal 5xx but the captured evidence was actually a 400 validation error, not a
real internal-dependency 5xx. This file supersedes that gap with a re-proven, genuine repro.

## Summary

- **Status:** genuine internal 5xx reproduced. Client sees a static, generic 500 body. Private
  telemetry (stderr `tracing::error!`) shows a sanitized OIDC-discovery-failure classification.
  No credential/URL/canary leaks to the client. Rust OTel/Jaeger export is real and wired at the
  CLI entrypoint, but is not applicable evidence for this specific failure (explained below) —
  reported honestly rather than fabricated.
- The initial repro was a pure-configuration test against an isolated relay instance built from
  `feat/035-p0-observability-contract` HEAD. Parent review of that repro's evidence surfaced a
  real private-telemetry URL/canary leak in stderr (see the CORRECTION section below); one file,
  `packages/rust-tools/infrastructure/src/auth.rs`, was then fixed to close it, and the repro was
  re-run against the fixed source.

## Why this is a genuine internal 5xx, not a disguised 400

Code path used: `packages/rust-tools/infrastructure/src/transport.rs`, the `Remote`-mode auth
middleware (function around lines 275–430 at HEAD).

Ordering, confirmed by reading the source before reproducing:

1. Admission/rate-limit check (top of middleware) — passed (not the failure).
2. `SecurityMode::Remote` branch entered.
3. `trusted_proxy_https(...)` check (HTTPS-termination trust) — passed, using
   `--trusted-proxy --trusted-proxy-cidr 127.0.0.1/32` plus a real `x-forwarded-proto: https`
   header from a loopback peer.
4. `oauth_issuer`/`oauth_audience` presence check — passed (both configured).
5. `Authorization: Bearer <token>` header presence/prefix check — passed.
6. `auth::parse_structurally_plausible_jwt(token)` — a **cheap, pre-network** structural check
   (3 non-empty base64url segments, decodable header JSON, `alg` ∈ {RS256, ES256}, `kid` present).
   This is deliberately *before* any network I/O and would reject a malformed token with 401
   (`invalid_token`) — that is the disguised-400/401 case the task warned about, and it is **not**
   what happened here: our token has a proper 3-segment structure, a decodable RS256/kid header,
   and base64url-valid (if semantically meaningless) payload/signature segments, so it **passes**
   this check and the code proceeds past it.
7. Only now does the middleware call `auth::fetch_discovery(client, discovery_url)` — a **real
   outbound HTTP GET** to `{oauth_issuer}/.well-known/openid-configuration`. This is the actual
   OIDC dependency call. It fails because `oauth_issuer` was configured to
   `https://127.0.0.1:1/...` — a real TCP port with nothing listening (connection refused).
8. On `Err(msg)` from that fetch, the code (lines ~404-419) logs
   `tracing::error!(event = "relay.auth.discovery", outcome = "error", detail = safe_log_field(&msg))`
   and returns `StatusCode::INTERNAL_SERVER_ERROR` with the **static** body
   `McpError::Internal("OIDC discovery unavailable".into())`.

So the 500 is generated by a genuine downstream-dependency failure (JWKS/OIDC discovery
unreachable) reached only after admission, HTTPS-trust, config-presence, and structural-JWT
checks all passed — not a disguised input-validation rejection. A malformed/garbage token never
reaches step 7; it is rejected at step 6 with 401, which is exactly the negative case this repro
avoids.

bare `http://127.0.0.1:1` — this satisfies both "real network-level connection-refused target"
and the relay's own config validation.

Sent a real HTTP request with a syntactically-valid-but-uncheckable JWT (arbitrary RS256 header

## CORRECTION — private stderr `detail` also sanitized (parent review finding)

The first repro pass (below) showed `detail` containing the raw unreachable issuer URL and the
canary marker in plaintext stderr. On review, that violates the frozen contract's rule #2 more
strictly than the original code comment assumed: "No secret ... arbitrary URL/query ... enters
telemetry, logs, traces, labels, console, **or stderr**" — there is no private-only carve-out.
`reqwest::Error`'s `Display` impl embeds the request URL by construction
(`"error sending request for url (...)"`), so interpolating it via `format!("... {e}")` leaked the
URL into `stderr` even though `safe_log_field`/`redact_secrets` ran on the resulting string
(neither strips bare URLs — they only mask credential-shaped substrings).

Fixed in `packages/rust-tools/infrastructure/src/auth.rs`: added `classify_reqwest_error()`,
mapping a `reqwest::Error` to one of a fixed set of static, low-cardinality labels
(`timeout`/`connect_failed`/`http_error_status`/`response_decode_failed`/`body_error`/
`request_failed`) via `reqwest::Error`'s own `is_timeout()`/`is_connect()`/etc. classifier methods
— never interpolating the error's `Display` text. `fetch_discovery`/`fetch_jwks` now return
`"oidc_discovery_fetch_failed:connect_failed"`-shaped strings instead of raw messages. Re-ran the
exact same repro below against a `cargo build --release` from the fixed source; both client and
stderr captures were replaced with the corrected run. `cargo check --workspace --all-targets
--all-features` passed after the change.

## (c) Jaeger/OTel — honest scope statement, not fabricated

Rust OTel export **is genuinely wired**: `packages/rust-tools/infrastructure/src/telemetry.rs`'s
`init_telemetry()` is called unconditionally at `cli/src/main.rs:30` for every `ai-tools`
subcommand including `relay`, and when `NUXT_OTEL_ENABLED=true` it builds a real OTLP-gRPC
exporter and installs a `tracing_subscriber::registry()` with only an OTel layer (no stderr fmt
layer in that branch).

We first ran with OTel enabled (`NUXT_OTEL_ENABLED=true`, `NUXT_OTEL_JAEGER_ENDPOINT=http://127.0.0.1:4317`,
pointed at the pre-existing `plan035-jaeger` container) and reproduced the same 500. Querying
Jaeger's API (`GET /api/traces?service=ai-code-relay`, the hardcoded `service.name` in
`telemetry.rs` — the `NUXT_OTEL_SERVICE_NAME` env var is documented in that file as
"informational only on the Rust side" and does not change the exported service name) returned
only the process-startup span (`ai_tools.startup`) — **no span at all for the failed `/mcp`
request**, and therefore no exported span event carrying the `relay.auth.discovery` failure.

Reading the source confirms why: no `tracing::info_span!`/`#[instrument]` wraps the axum request
handler or the remote-mode auth middleware in `transport.rs`, so the `tracing::error!` call at the
discovery-failure site has no active span to attach to. `tracing-opentelemetry` only exports
events that occur inside a span; a bare event with no active span is not exported to Jaeger at
all under the current instrumentation. This matches the existing plan-035 evidence
(`README.md`'s Phase-10 "Operator lookup flow" section) which already documents that Rust
stderr-JSON is the sole diagnostic channel for this kind of failure and that no OTel-logs bridge
exists.

**Conclusion, stated plainly rather than fabricated:** for this specific auth-middleware
dependency-failure path, Jaeger export is not an applicable proof surface today — not because
OTel isn't wired (it is, and does work for the `ai_tools.startup` span and for genuine
request-handling spans deeper in `transport.rs`'s dispatcher, per `audit()` call sites at lines
691/714/931), but because no span currently wraps the remote-mode auth middleware where this
particular `tracing::error!` fires. We did not claim a Jaeger capture we didn't have. The private
stderr telemetry in (b) is the sole operator-visible sink for this failure today, and it was
independently confirmed non-empty, correctly classified, and canary-scoped-as-expected (private
only).

For completeness, the canary was also checked against the OTel-enabled run's client response and
Jaeger query — see (d).
