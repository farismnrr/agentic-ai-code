---
name: 018-sidebar-single-fetch
description: sidebar workspaces + conversations used to be two chained client-side composable calls; that chaining repeatedly broke Nuxt SSR context and silently dropped data — now one BE endpoint (GET /api/sidebar) returns both joined.
metadata:
  type: project
---

`app/layouts/default.vue` used to load the sidebar by orchestrating two separate composables client-side: `useWorkspaces().loadAll()` and `useConversations().loadAll()`, chained (`loadWorkspaces(settingsPromise).then(loadConversations)`) or placed side-by-side in the same `Promise.allSettled`. Live-verified across three rounds of debugging: **every extra await/`.then()` boundary inserted between the outer async function's synchronous start and the point a composable's body actually runs breaks Nuxt's SSR composable context** (`useRequestFetch()` inside `loadAll()` throws `NUXT_E1001`), and `Promise.allSettled` swallows that rejection with zero visible symptom — see [[015-composable-after-await-breaks-ssr-context]]. This is the same trap, but it kept resurfacing in a new shape every time the fix moved the failure point instead of removing it: fixing `loadWorkspaces()`'s invocation still left `loadConversations()` broken because it was chained via `.then()`; fixing that too still left the sidebar fragile to the next well-intentioned restructure.

**The actual fix wasn't another invocation-order patch — it was removing the client-side join entirely.** `GET /api/sidebar` (`server/api/sidebar.get.ts`) now does the two-query join server-side and returns `{ workspaces, conversations }` in one response; `app/composables/useSidebarData.ts` is one `fetch()` call that assigns both `useState` refs directly. There is nothing left to chain, so there's no boundary left to break.

**How to apply:** this generalizes past this one screen. **BE endpoints must return response JSON already shaped for what the screen needs — joined, paginated, filtered — server-side.** FE composables should not combine, re-key, or sequence multiple endpoint calls to assemble one screen's data; each additional client-side async step (even one that looks harmless, like a `.then()` or a second entry in a `Promise.allSettled`) is a fresh place for this exact class of bug to reappear. If a screen needs data from more than one table, that's a reason to add a joined endpoint, not a reason to fetch twice and merge client-side. See `.agents/knowledge/conventions.md` for where this rule lives as a standing convention.
