`server/utils/langgraph-chat.ts` bridges `langchain`'s `createAgent({ model, tools })` (chat mode's tool loop, see [[018-chat-mode-langgraph]]) into `ai@7`'s `createUIMessageStream({ execute: ({ writer }) => ... })`. Three rounds of live review turned up real API mismatches — none of this is guessable from the AI SDK v4 docs/muscle memory, which is exactly what the first draft got wrong:

- **`UIMessageStreamWriter` only has `write()`, `merge()`, `onError`.** There is no `writeTextDelta`/`writeCallTool`/`writeToolResult`/`finish()` — those are v4-era method names that don't exist on `ai@7.0.56`. Every chunk goes through `writer.write({ type: '...', ... })` with the exact `UIMessageChunk` union shape.
- **Text chunks need `text-start` before the first `text-delta`, and a `text-end` closing it** — `ai@7`'s client-side stream processor throws `UIMessageStreamError: Received text-delta for missing text part with ID "..."` if a delta arrives with no open text part. Each text run needs a fresh id (`text-${textIndex}`) since a response can have text, then a tool call, then more text.
- **Tool parts persisted to the DB must use `ai@7`'s real `DynamicToolUIPart` shape** — flat `{ type: 'dynamic-tool', toolCallId, toolName, state, input, output? }`, not an invented `{ type: 'tool-invocation', toolInvocation: {...} }` (that's the v4 shape). `state` must be one of `'input-streaming' | 'input-available' | 'approval-requested' | 'approval-responded' | 'output-available' | 'output-error'` — `'call'`/`'result'` compile fine (the array is typed `any[]`) but aren't valid, and `@nuxt/ui`'s `isToolStreaming()` treats anything outside `{'approval-requested','output-available','output-error','output-denied'}` as still-streaming — so an invalid state means the tool card shows a permanent loading spinner after reload even though the result already rendered.
- **The live `tool-input-available`/`tool-output-available` writer chunks need `dynamic: true`** — omitting it makes `ai@7`'s live-stream reducer build a static `tool-<name>` part while the DB-persisted copy (built by hand) is `dynamic-tool`, so the same tool call renders with a different part `type` live vs. after reload.
- **On a mid-stream error, any tool part still sitting in `input-available` must be resolved to `output-error` before persisting** — otherwise a network blip between `on_tool_start` and `on_tool_end` saves a message with a tool call that never resolves, and reload shows an open-ended spinner with no error shown (the `error` chunk written to the live stream isn't itself part of the persisted `parts` array).
- **`createReactAgent` is deprecated in `@langchain/langgraph/prebuilt`** — it moved to `langchain`'s `createAgent({ model, tools })` (renamed param: `llm` → `model`). Migrating means adding `langchain` as a dependency, not a signature tweak; `@langchain/langgraph` itself becomes an unused direct dependency once nothing imports it — remove it, don't leave it as dead weight in `package.json`.

**Deliberately deferred, not fixed:** `agent.streamEvents(..., { version: 'v2' })` is what's implemented. `langchain`'s own types flag `v2` as "legacy, internal-only" and point to `version: 'v3'`, which returns a `Promise<AgentRunStream>` — a structurally different, promise-based, non-iterable API, not a drop-in flag flip. Migrating to `v3` is a full event-loop rewrite and was explicitly left for a future pass rather than folded into this bugfix chain.

**How to apply:** if agent mode (deferred per [[018-chat-mode-langgraph]]) also moves onto LangGraph/`langchain` later, reuse this bridge rather than re-deriving the writer API and part shapes from scratch — and revisit the `v3` migration at that point, since a bigger rewrite is more justified alongside a bigger feature than alone.
