A `:ui`/`:ui="{ slot: {...} }"` override with a wrong slot key doesn't fail at runtime — Vue just ignores the unknown prop key silently, so the class never reaches any element and the intended effect (in this case, entrance animations) quietly does nothing.

**Why this matters:** `pnpm build` and `pnpm run lint` don't catch it — Rollup/eslint have no opinion on object-literal shape. Only `vue-tsc -p .nuxt/tsconfig.json --noEmit` (the real gate per [[007-typecheck-gate-was-silent]]) reports it, as `TS2353: Object literal may only specify known properties`. It was missed once already in this exact scenario: plan 013's motion pass shipped `:ui="{ base: ... }"` on `UChatReasoning` (real slot is `content`, not `base`; `header` should be `trigger`) and `:ui="{ message: { base: ... } }"` on `UChatMessages` (there is no `message` slot at all — `UChatMessages` only exposes `root`/`indicator`/`viewport`/`autoScroll`; per-message styling goes through the `user`/`assistant` props' own `ui` key, e.g. `:assistant="{ ui: { root: '...' } }"`, since each message renders as a `UChatMessage` with its own slot set: `root`/`header`/`container`/`body`/`leading`/`content`/`actions`). The PR still passed `nuxt build` and merged to `dev` before this was caught in a follow-up review.

**How to apply:** before trusting a `:ui` override on any Nuxt UI component, check its real slot names — `mcp__nuxt-ui__get-component` with `sections: ["theme"]` (or `["api"]` for the prop-level `ui` type) — rather than guessing common names like `base`/`header`/`message`. When reviewing or writing `:ui` props, run `vue-tsc -p .nuxt/tsconfig.json --noEmit`, not just `nuxt build`, or the mistake ships silently.
